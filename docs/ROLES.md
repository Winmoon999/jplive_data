# 分工與流程（jplive × 日本演唱會神器）

最後更新：2026-10-29。有改動請同步更新 Project 內的「分工文件」。

## 目標
使用者（Winmoon）要上架 Google Play 的 Android app「日本演唱會神器」：月曆顯示日本演唱會，使用者可選擇追蹤的歌手，資料從這個公開儲存庫的 `main` 讀取。資料由 jplive skill 每天自動整理，經使用者人工確認後才進 `main`。

## 角色與責任
| | skill 端（jplive） | app 端 |
|---|---|---|
| 負責 | 搜尋與核對 Live 資訊、維護正本資料庫、抓取紀錄、報告、排程提示詞 | Android app 的讀取與介面、發布腳本、衍生檔格式、Play 上架準備、`CLAUDE.md`／本文件 |
| 修改範圍 | `.claude/skills/jplive/**`、`reports/` | `scripts/`、`docs/`、`CLAUDE.md`、app 程式（在使用者電腦） |
| 不做 | 不改 app、不改發布腳本 | 不找演唱會資料 |
| 執行環境 | 雲端排程／雲端工作階段 | 使用者電腦的 Android Studio（build APK／AAB） |
| 人工把關 | — | 使用者在 GitHub 按 Merge |

## 資料流
```
skill 查資料 → 更新正本（分支）→ validate.py → publish.py（重新產生衍生檔）
→ 開 Pull Request → 使用者人工確認差異 → 使用者按 Merge 進 main
→ 手機 app 下次開啟時讀取 main 的 index.json 與 artists/*.json
```

## 兩條資料線
1. **日常更新**：skill 每天（台北 05:00＝日本 06:00）對 `tracked: true` 的藝人增量查詢，推 `data-update` 分支並開 PR。排程要等第一次手動試跑通過、並經使用者同意後才建立。
2. **一次性對照（目前進行中）**：app 端先前整理了 7 位藝人、22 個活動的「副本」，在分支 `data-review`。skill 端獨立核對、輸出差異報告，不改副本。使用者確認後，由 app 端整合進正本，並把副本凍結放進 `old/<日期>-app-seed/`（內部結構維持原樣）。

## 副本核對流程
1. skill 端取 `data-review` 的 `artists/*.json` 與 `SCHEDULE.md`，對每一筆（日期、場館、開場／開演、票務、狀態、來源等級）獨立查證，不看副本寫的結論再抄一遍。
2. 輸出 `reports/compare-<日期>.md`，每筆分類：
   - ✅ 一致（附官方來源）
   - ⚠️ 不一致（兩邊的值與各自來源）
   - ❓ 無法驗證（官方讀不到，說明試過什麼）
   - ➕ skill 找到副本沒有的活動
   - ➖ 副本有、skill 找不到的活動
3. 不直接修改副本。使用者看報告後決定採哪邊，再交由 app 端整合。
4. 試跑新藝人：上田麗奈、fripSide、愛繆（あいみょん，使用者已確認）、Aimer。用新格式，開 PR，不進 `main`。

## 使用者新增藝人（第二階段，尚未開始）
app 把使用者輸入的藝人名稱送到小型中介服務（Cloudflare Workers，由 app 端寫程式、使用者自己部署），服務在這個儲存庫建立帶固定標籤的 Issue，skill 讀 Issue 作為待處理佇列。名稱需限制長度與字元，視為不可信資料；skill 先用別名表比對，比對不到標「待確認」不直接建檔。需等第一階段穩定後再做。

## 待決定／風險
- 用個人訂閱方案的排程服務一個公開 app，是否符合服務條款，**公開上架前必須先確認**；不允許的話改用 API 並計費。
